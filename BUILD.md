# Сборка приложения

Сборкой занимается EAS Build — Expo собирает на своих машинах, локально
ни Android SDK, ни Xcode не нужны. Запускается всё через GitHub Actions:
**Actions → EAS Build → Run workflow**, там выбираются платформа
(`android` / `ios` / `all`) и профиль. Ссылка на готовый файл появляется
в Summary запуска.

При `all` запускаются две независимые задачи, по одной на платформу.
Это не мелочь: iOS без настроенных ключей Apple падает сразу (см. ниже),
и одной командой на обе платформы он утащил бы за собой Android.

Профили описаны в `eas.json`:

| Профиль | Android | iOS |
| --- | --- | --- |
| `preview` | APK, ставится напрямую | ad-hoc `.ipa` для зарегистрированных устройств |
| `production` | AAB для Google Play | сборка для App Store / TestFlight |
| `simulator` | — | `.app` для iOS Simulator |

Ключи Supabase (`EXPO_PUBLIC_SUPABASE_URL`, `EXPO_PUBLIC_SUPABASE_ANON_KEY`)
зашиты в `env` профилей — это публичный anon-ключ, он и должен попадать
в клиент. Токен Expo лежит в секрете репозитория `EXPO_TOKEN`.

## Supabase

Серверная часть живёт в `supabase/`. Всё в ней ставится вручную, один раз
(и после каждой правки схемы или функций):

1. **Схема.** SQL Editor → вставить целиком `supabase/schema.sql` → Run.
   Файл идемпотентный, прогонять можно сколько угодно раз в любом
   состоянии базы.
2. **Edge Functions.** По одной команде на каждую:

   ```
   supabase functions deploy auth-helper
   supabase functions deploy delete-account
   supabase functions deploy send-push
   supabase functions deploy tournament
   ```

   Либо кнопкой, без локального CLI: Actions → **Deploy functions** → Run
   workflow, в поле вписаны `tournament send-push`. Нужны два секрета
   репозитория — `SUPABASE_ACCESS_TOKEN` (личный токен со страницы
   [account/tokens](https://supabase.com/dashboard/account/tokens)) и
   `SUPABASE_PROJECT_REF` (поддомен адреса проекта). Токен живёт только в
   секретах GitHub.

| Функция | Зачем |
| --- | --- |
| `auth-helper` | вход по имени пользователя, не раскрывая клиенту почту аккаунта |
| `delete-account` | удаление аккаунта (нужен service role) |
| `send-push` | пуши о заявках в друзья и вызовах на бой |
| `tournament` | недельный турнир: регистрация, посев по рейтингу, сведение матчей, начисление медалей, оповещения о записи и старте |
| `shop` | кошелёк и магазин: баланс, покупки, расходники, заказы, платежи |
| `yookassa-webhook` | подтверждение оплаты от ЮKassa (деплоить с `--no-verify-jwt`) |

Без задеплоенной `tournament` недельный турнир недоступен: экран не
падает, но показывает, что нужен облачный аккаунт.

### Оповещения о турнире вовремя

`tournament` шлёт два пуша: «открылась запись» — всем, у кого есть
устройство в `push_tokens`, и «турнир начался» — тем, кто попал в сетку.
Оба уходят ровно один раз, потому что отправка висит на тех же двух
записях в базе, которые и так защищены от повторения: вставка строки
новой недели и закрытие регистрации.

Беда в том, что неделя переворачивается лениво — когда кто-нибудь
откроет экран турнира. Тогда же уйдут и оповещения, то есть, возможно,
через сутки после самого события. Чтобы они приходили вовремя, её дёргает
по расписанию `.github/workflows/tournament-tick.yml`. Ему нужны три
секрета репозитория (Settings → Secrets and variables → Actions):

| Секрет | Значение |
| --- | --- |
| `SUPABASE_PROJECT_REF` | поддомен адреса проекта (его же просит деплой) |
| `SUPABASE_ANON_KEY` | anon-ключ проекта — он и так лежит внутри приложения |
| `TOURNAMENT_TICK_SECRET` | любая длинная случайная строка |

`TOURNAMENT_TICK_SECRET` достаточно положить сюда: воркфлоу **Deploy
functions** сам запишет это же значение в секреты проекта, так что
команду `supabase secrets set` можно не выполнять — достаточно после
добавления секрета один раз прогнать деплой.

Дальше `.github/workflows/tournament-tick.yml` раз в четверть часа стучится
в функцию с этим секретом. Пока секретов нет, задача просто пропускается,
и всё работает по-старому — лениво.

Без задеплоенной `shop` магазин у облачного аккаунта не покажет баланс и
не даст купить за очки. Локальный аккаунт (без `.env`) магазином
пользуется как раньше — кошелёк у него лежит на самом телефоне.

**Важно про деньги и медали.** Баланс, покупки и заказы считает сервер.
Ни одна из таблиц `tournament_medals`, `shop_purchases`, `shop_inventory`,
`shop_orders` не имеет политик insert/update/delete — писать в них может
только Edge Function под service role. Цены тоже лежат на сервере
(`supabase/functions/shop/index.ts`), клиент их не присылает: он говорит
«хочу купить вот это за очки», а сколько это стоит и хватает ли баланса,
решается на той стороне. Проверка баланса и списание идут одним SQL-вызовом
под блокировкой, поэтому два быстрых нажатия не уведут баланс в минус.

Цены продублированы в двух местах — в `src/shop/catalogue.ts` и в функции.
Их синхронность проверяет тест `cataloguePriceParity`: добавили товар в
каталог и забыли в функции — упадут тесты, а не продадите что-то даром.

**Мессенджер.** Правка сообщений, пересылка, непрочитанное в группах и
«был(а) в сети» — это только схема, отдельной Edge Function им не нужно:
достаточно прогнать `supabase/schema.sql` заново. Добавляются колонки
`edited_at` и `forwarded_from` в `messages` и `group_messages`, таблица
`group_reads` (засечка «докуда дочитал» у каждого участника группы),
колонка `profiles.last_seen_at` и две функции — `edit_message` и
`edit_group_message`.

Правка идёт через функцию, а не через политику UPDATE, намеренно. У
`messages` политика на обновление принадлежит получателю — ею сообщение
помечается прочитанным. Добавить рядом вторую, «обновлять может
отправитель», значит сложить их через OR и открыть отправителю всю строку,
включая `read`: он смог бы сам проставить галочку прочтения на своём
сообщении. Функция сужает право до двух колонок и проверяет авторство сама.

**Вложения.** Фото и файлы лежат в ведре `chat-media`, его тоже создаёт
`schema.sql`. Ведро закрытое, в отличие от `avatars`: аватар видит кто
угодно, а фото из личной переписки — только её участники. Поэтому картинки
в пузырях грузятся по подписанным ссылкам на час, а не по постоянным.

Право на файл определяется его путём: `dm/<id1>_<id2>/…` — доступ у двоих,
чьи id стоят в имени папки, `group/<id группы>/…` — у участников группы.
Проверяет это функция `can_use_chat_media`, на неё сослана политика
`storage.objects`. Удалять может только тот, кто загрузил.

Разрешённые типы — картинки и `application/octet-stream`. Всё, что не
картинка, кладётся как octet-stream, даже если это PDF: иначе браузер,
открыв подписанную ссылку на присланный HTML, выполнил бы его прямо на
домене хранилища, где лежат файлы всех переписок. Настоящий тип при этом не
теряется — его несёт расширение в имени файла, по нему система и открывает
скачанное.

Потолок — 10 МБ на файл, он стоит и на ведре, и в клиенте (`attachments.ts`).
Фото перед отправкой ужимается до 1600px по длинной стороне.

**Голосовые.** Третий вид вложения рядом с фото и файлом: то же ведро, те же
политики, добавляются только колонка `attachment_duration_ms` и звуковые
типы в списке разрешённых. Голосовое, в отличие от прочих файлов, хранится
под настоящим типом (`audio/mp4` на телефоне, `audio/webm` в вебе) — плееру
он нужен, чтобы запись заиграла. Это безопасно по той же причине, что и у
картинок: браузер аудио проигрывает, а не исполняет. Список типов закрытый,
не `audio/*`.

Запись — моно 24 кГц, 32 кбит/с (`voiceRecorder.ts`), около 4 КБ в секунду:
минута речи — четверть мегабайта. Пресет `HIGH_QUALITY` из expo-audio для
этого не годится, он стерео 44,1 кГц 128 кбит/с — это настройки для музыки.
Потолок записи — 5 минут, по его достижении запись не отбрасывается, а
отправляется.

Микрофон требует разрешения: плагин `expo-audio` в `app.json` с текстом
запроса. Без пересборки (не OTA) разрешение на устройстве не появится.

Прогнать схему обязательно, и до выкладки сборки. Клиент запрашивает
`edited_at` и `forwarded_from` тем же SELECT, которым берёт текст
сообщений, так что на базе без этих колонок запрос падает целиком —
переписка и список чатов будут пустыми, а не «как раньше».

## Турнир: счёт считает сервер

Раньше приложение само присылало счёт сыгранной партии, и функция ему
верила. Теперь партию сначала «сдают»:

1. приложение просит начать партию (`action: 'start'`) и получает **сид**;
2. играет ровно ту викторину, которая из этого сида получается — генератор
   вопросов детерминирован;
3. присылает не счёт, а **что было выбрано** в каждом вопросе;
4. функция считает счёт по ключу ответов
   (`supabase/functions/_shared/tournamentKey.ts`).

Ключ — это индекс верного варианта для каждого вопроса каждой из 2000
возможных партий. Его собирает настоящий генератор приложения, а тест
`src/tournament/__tests__/answerKey.test.ts` падает, если ключ от
генератора отстал.

### Когда меняется состав вопросов

Добавили персонажа, тайтл, тип вопроса, поменяли длину партии — ключ
устаревает, и тест об этом скажет. Тогда, **строго в этом порядке**:

```bash
UPDATE_TOURNAMENT_KEY=1 npx jest src/tournament/__tests__/answerKey.test.ts
# задеплоить функцию tournament, затем выпустить сборку
```

Ключ и сборка несут одну и ту же версию. Сборка, собранная до изменения,
получит «обновите приложение» вместо того, чтобы её ответы проверяли по
ключу от других вопросов. Менять состав посреди идущего турнира не стоит:
игроки на старой сборке не смогут доиграть, пока не обновятся.

### Что ещё ограничено

- На одну партию — **три старта**; каждый сдаёт новые вопросы. Иначе можно
  было бы выходить и заходить, пока не выпадет лёгкий набор.
- Ответы принимаются в окне от 4 секунд до 10 минут с момента старта.
- `round_results` (недельная и сезонная таблицы): счёт не больше длины
  раунда, раунд не длиннее 30 вопросов, время ставит сервер, не чаще раза
  в 5 секунд и не больше 600 раундов в сутки.
- Место в сетке считается из статистики **с потолком**: каждый рекорд не
  выше длины своего раунда, учитываются только существующие категории.

### Чего это не даёт

Честно о границе. Вопросы и ответы лежат в самом приложении — иначе оно не
работало бы без сети. Значит, тот, кто разберёт сборку и напишет бота, всё
ещё может сыграть партию «идеально» через честный протокол. Закрыт дешёвый
путь — отправить `7` одним запросом; дорогой остался.

То же со статистикой обычных раундов: сервер их не видит и проверить не
может, поэтому она ограничена, а не подтверждена. Подделанный профиль
может выглядеть как игрок, прошедший всё, но не выше.

Практический вывод: **мерч за очки отправляет человек** — перед отправкой
стоит взглянуть на историю победителя (таблица `tournament_games`: счёт и
время сдачи каждой партии). Семь из семи за пять секунд во всех партиях
подряд видно сразу.

## Оплата картой (ЮKassa)

Через ЮKassa оплачивается **только мерч**. Косметика и расходники тоже
продаются за деньги, но через биллинг самого магазина приложений — это
отдельный раздел ниже, и это не ограничение движка, а правило Google и
Apple: цифровые товары внутри приложения обязаны идти через биллинг
магазина, а физические — наоборот, через сторонний эквайринг.

Переключатель `DIGITAL_RUB_ENABLED` (в `supabase/functions/shop/index.ts`
и зеркало в `src/shop/payment.ts`, синхронность проверяет тест) переводит
и косметику на ЮKassa. Включать только если приложение перестало
распространяться через магазин с таким правилом — например, прямой APK.

### Что нужно завести

1. ИП, ООО или самозанятость и магазин в ЮKassa.
2. Оферта и правила возврата — опубликованные, со ссылкой из приложения.
3. Ключи, только в секретах функций (в `.env` приложения им не место):

```bash
supabase secrets set YOOKASSA_SHOP_ID=... YOOKASSA_SECRET_KEY=...
supabase functions deploy shop
supabase functions deploy yookassa-webhook --no-verify-jwt
```

4. В личном кабинете ЮKassa указать URL уведомлений на
   `https://<project>.functions.supabase.co/yookassa-webhook`
   и включить события `payment.succeeded` и `payment.canceled`.

### Чеки по 54-ФЗ

Чеки покупателям-физлицам обязательны, но отправлять их без подключённого
решения и с неверным кодом НДС — значит ломать каждый платёж. Поэтому
блок чека **выключен по умолчанию** и включается отдельно, когда касса
подключена:

```bash
supabase secrets set YOOKASSA_RECEIPTS=1 YOOKASSA_VAT_CODE=1
```

`YOOKASSA_VAT_CODE` должен соответствовать вашему режиму
налогообложения — значение по умолчанию (1, «без НДС») подходит не всем.

### Как это работает

Заказ создаётся со статусом `awaitingPayment`, функция `shop` делает
платёж в ЮKassa (ключ идемпотентности — id заказа, поэтому повтор запроса
не спишет деньги дважды) и возвращает приложению ссылку на страницу
оплаты. Приложение открывает её и ждёт возврата по диплинку.

Оплаченным заказ делает **только вебхук**, и он не верит тому, что ему
прислали: из тела берётся один лишь id платежа, после чего статус
запрашивается у ЮKassa напрямую. Возврат из браузера доказательством
оплаты не считается — по нему приложение просто перечитывает состояние.

## Покупка за деньги через биллинг магазина

Косметика, рамки и расходники продаются за реальные деньги через **Google
Play Billing** и **Apple StoreKit**. Мерч туда не попадает никогда: для
физических товаров биллинг магазина запрещён ровно так же, как для
цифровых обязателен. Решает это одна функция — `moneyRail` в
`src/shop/products.ts`, и её проверяет тест.

Без настройки ниже всё работает как раньше: денежной кнопки у косметики
просто нет, продаётся за медали. Приложение не показывает цену, которую
некому принять.

### 1. Товары в консолях

Идентификаторы товаров перечислены в `src/shop/products.ts` (и зеркалом в
функции `shop`). **Их нельзя переименовать после первой продажи** — ни
Google, ни Apple этого не позволяют, поэтому список и выписан руками, а не
выводится из id предмета. Создать нужно ровно эти:

| Товар | Product ID | Тип | ₽ | Тариф $ |
| --- | --- | --- | --- | --- |
| Подсказка 50/50 ×1 | `item_hint_1` | расходуемый | 49 | $0.99 |
| Заморозка серии | `item_freeze` | расходуемый | 99 | $1.99 |
| Пропуск вопроса ×3 | `item_skip_3` | расходуемый | 129 | $2.99 |
| Подсказка 50/50 ×5 | `item_hint_5` | расходуемый | 199 | $3.99 |
| Рамка «Аврора» | `frame_aurora` | нерасходуемый | 149 | $2.99 |
| Рамка «Уголёк» | `frame_ember` | нерасходуемый | 149 | $2.99 |
| Рамка «Контур» | `frame_circuit` | нерасходуемый | 179 | $3.99 |
| Рамка «Лепестки» | `frame_petals` | нерасходуемый | 199 | $3.99 |
| Рамка чемпиона | `frame_champion` | нерасходуемый | 300 | $5.99 |
| Рамка «Вечность» | `frame_eternal` | нерасходуемый | 400 | $7.99 |
| Аватарка «Котик» | `avatar_neko` | нерасходуемый | 200 | $3.99 |
| Аватарки за 250 | `avatar_sakura`, `avatar_ember`, `avatar_mint`, `avatar_sunny` | нерасходуемый | 250 | $4.99 |
| Аватарки за 300 | `avatar_shadow`, `avatar_frost`, `avatar_violet` | нерасходуемый | 300 | $5.99 |

**Тип важнее цены.** Расходуемый (consumable) — это расходники, их покупают
снова и снова. Нерасходуемый — косметика, её покупают один раз.
Перепутать — значит получить одну из двух классических поломок: уже
«потреблённая» косметика перестанет восстанавливаться на новом телефоне, а
непотреблённый расходник нельзя будет купить второй раз. В коде то же
различие живёт в `isConsumableSku`, и тест сверяет его с каталогом.

Долларовый тариф взят с запасом на комиссию магазина: 30% стора плюс 6%
налога съедают почти треть, поэтому прямой пересчёт рублёвой цены по курсу
дал бы меньше, чем задумано. Ступени выше рассчитаны так, чтобы чистыми
приходило не меньше рублёвой цены. Если подключён льготный процент (Google
Play первый $1 млн, App Store Small Business Program — 15% вместо 30%),
прайс можно не трогать: это просто +20–25% чистыми.

### 2. Доступ к API Google Play

Проверять чек — значит спрашивать у Google. Для этого нужен сервисный
аккаунт:

1. Google Play Console → Настройки → **Доступ к API** → связать проект
   Google Cloud.
2. В Google Cloud создать сервисный аккаунт, выдать ему ключ в формате
   **JSON**.
3. Вернуться в Play Console и дать этому аккаунту право
   **«Просмотр финансовых данных»** (этого достаточно для
   `purchases.products`).

### 3. Доступ к API App Store

1. App Store Connect → Users and Access → **Integrations** → In-App
   Purchase → сгенерировать ключ, скачать `.p8` (даётся один раз).
2. Запомнить **Key ID** и **Issuer ID** с той же страницы.

### 4. Секреты функций

```bash
supabase secrets set \
  GOOGLE_PLAY_SERVICE_ACCOUNT="$(cat service-account.json)" \
  ANDROID_PACKAGE_NAME=com.animequiz.app \
  APPLE_IAP_KEY_ID=XXXXXXXXXX \
  APPLE_IAP_ISSUER_ID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx \
  APPLE_IAP_PRIVATE_KEY="$(cat AuthKey_XXXXXXXXXX.p8)" \
  IOS_BUNDLE_ID=com.animequiz.app

```

Ключам место только здесь. В `.env` приложения их быть не должно: оттуда
они попадут в сборку, а из сборки их достанет кто угодно.

Задан только Google — работает Android, iOS отвечает
`storeBillingUnavailable`, и наоборот. Не задано ничего — косметика
продаётся за медали, как до всего этого.

### 5. Схема и сборка

**Схему прогнать обязательно** — появились таблица `shop_store_purchases`,
функция `shop_claim_store_purchase` и третье значение в `paid_with`.

**Пересобрать обязательно.** Биллинг — нативный модуль (`expo-iap` в
`plugins` в `app.json`), в Expo Go его нет и быть не может. Там и в вебе
магазин открывается и продаёт за медали, а денежная кнопка не появляется.
Проверять покупки — на preview- или production-сборке: Android через
тестировщиков лицензий (Play Console → Настройки → Тестирование
лицензий), iOS через Sandbox-аккаунт или TestFlight.

### Как это работает

Платёж принимает магазин, предмет выдаёт сервер, и между ними нет доверия:

1. Приложение открывает окно оплаты магазина и помечает покупку тем, **кто
   платит** — Apple получает id аккаунта как UUID, Google его же, но
   хешированным (он виден покупателю в истории покупок).
2. Магазин возвращает чек. Приложение не верит ему ни на грош и отдаёт
   серверу (`action: 'claim'` в функции `shop`).
3. Сервер спрашивает у Google или Apple **своими ключами**, был ли платёж,
   и сверяет три вещи: оплачено ли, тот ли это товар, и тот ли это
   покупатель. Чек от клиента не доказательство — на рутованном телефоне
   его подделать несложно, и единственная причина, по которой это
   безопасно, — что проверка идёт мимо телефона.
4. Только после этого выдаётся предмет, и уникальный ключ в
   `shop_store_purchases` следит, чтобы один платёж выдал предмет один
   раз, сколько бы раз чек ни принесли.
5. И только после выдачи транзакция закрывается у магазина. Порядок
   важен в обе стороны: закрыть раньше — потерять единственное
   доказательство оплаты, если выдача не удалась; не закрыть вовсе —
   Google вернёт покупателю деньги через три дня.

Отсюда же **«Восстановить покупки»** в «Моих покупках»: если приложение
убили посреди оплаты, пропала сеть сразу после списания или покупатель
выбрал медленный способ оплаты, который дошёл через три дня, — платёж
лежит у магазина незакрытым. Эта кнопка (и тот же проход автоматически при
открытии магазина) его дозабирает. Apple, помимо прочего, прямо требует,
чтобы такая кнопка была.

Чего здесь нет намеренно: продажи медальных очков за деньги. Как только
очки начнут продаваться, они перестанут что-либо значить — об этом
`docs/shop-economy.md`. За деньги продаются вещи, а не валюта.

## RuStore

RuStore — третий магазин и только Android. Подключается он не так, как
Google и Apple, и причина одна, зато важная.

**У RuStore нет требования продавать цифровые товары через его биллинг.**
Он прямо допускает альтернативные платёжные решения и, по его же
материалам, **не берёт с них комиссию** ([блог
RuStore](https://www.rustore.ru/developer/blog/self-employed), [гайд по
публикации](https://fittin.ru/blog/kak-opublikovat-prilozhenie-v-rustore)).
Google и Apple ровно наоборот: там биллинг магазина обязателен, и именно
поэтому в приложении появился `iap.ts`.

Отсюда два пути, и они сильно разной стоимости.

### Путь А: продавать цифру через ЮKassa (дешевле)

Идея: в сборке для RuStore косметика идёт через тот же эквайринг, что и
мерч. Переключатель для этого уже есть — `DIGITAL_RUB_ENABLED`.

Выгода прямая: эквайринг — это около 3.5%, комиссия RuStore с его
собственного биллинга — порядка 15% (цифры в источниках расходятся, см.
ниже), а с альтернативных платежей RuStore не берёт ничего. На каждой
проданной рамке разница — процентов десять.

**Но одного переключателя не хватит, и это не мелочь.** На пути быстрой
покупки (`action: 'buy'`) платёж никто не создаёт: у цифрового предмета нет
заказа, значит нет ни запроса в ЮKassa, ни вебхука, который подтвердит
оплату. Включить флаг и больше ничего не делать — значит начать **выдавать
всю косметику бесплатно**. Сейчас эта дорога закрыта явным отказом
(`digitalRubNotBuilt`), и тест следит, чтобы отказ стоял раньше выдачи.

Что нужно дописать, чтобы путь А заработал:

1. В `action: 'buy'` при оплате деньгами — создавать платёж в ЮKassa так
   же, как это делает `action: 'order'`, и возвращать приложению ссылку на
   оплату.
2. Выдавать предмет **только по вебхуку**, а не сразу: сейчас вебхук умеет
   переводить в `paid` заказ, его придётся научить и выдаче предмета.
   Возврат из браузера доказательством оплаты не считается — это уже
   записано в разделе про ЮKassa и остаётся верным.
3. Сделать `DIGITAL_RUB_ENABLED` различимым по сборке. Сейчас это
   константа в двух файлах: включить её «только для RuStore» нельзя,
   включится везде, в том числе в сборке для Google Play, где это прямое
   нарушение правил. Нужна переменная окружения функции (например
   `DIGITAL_RUB=1`) плюс признак сборки на стороне приложения.
4. Снять отказ из пункта выше — но только вместе с пунктами 1–2.

Пока это не сделано, в RuStore-сборке косметика продаётся за медали, а мерч
за карту. Это рабочее состояние, ничего не ломается.

### Путь Б: биллинг RuStore (Pay SDK)

Нативный путь, если платежи нужны именно через магазин.

**Сначала два факта, которые решают, возможен ли он для вас вообще.**

- **BillingClient SDK отключён 1 августа 2026.** То, что лежит в их
  GitHub-репозитории `react-native-rustore-billing-sdk`, — обёртка именно
  над BillingClient, и она мертва. Актуален **RuStore Pay SDK**;
  документация для React Native есть ([миграционный
  гайд](https://www.rustore.ru/developer/blog/perekhod-s-billingclient-sdk-na-pay-sdk-polnyj-gajd),
  [интеграция для React
  Native](https://www.rustore.ru/help/sdk/pay/react-native/10-3-1)).
- **Платёжные инструменты RuStore с 1 февраля 2026 доступны только ИП и
  юрлицам.** Самозанятому биллинг RuStore подключить нельзя — для него
  остаётся путь А. Это стоит проверить до того, как трогать код.

Что понадобится помимо кода:

1. Аккаунт разработчика RuStore и опубликованное приложение (нужен
   `consoleApplicationId`).
2. Товары в консоли RuStore — под **теми же id**, что в
   `src/shop/products.ts`. Третий список id заводить не нужно и не стоит:
   id уже выбраны так, чтобы подходить всем трём магазинам.
3. SDK ставится **не из npm**, а из git-репозитория RuStore на GitFlic.
4. Правки в `AndroidManifest.xml`: `consoleApplicationId` (в Pay SDK он
   переехал из кода в манифест) и отдельный `intent-filter` с
   deeplink-схемой, по которой RuStore возвращает управление приложению.
5. **Своя сборка.** Expo-плагина у SDK нет, а Play Billing в сборке для
   RuStore не нужен — как и RuStore SDK в сборке для Google Play. Значит
   либо свой config plugin, либо prebuild, и отдельный профиль EAS.

Что придётся дописать в этом проекте (по аналогии с тем, что уже есть для
Google и Apple):

| Где | Что |
| --- | --- |
| `src/shop/products.ts` | третий рельс в `moneyRail` — для RuStore-сборки |
| новый модуль рядом с `src/shop/iap.ts` | обёртка над Pay SDK: наличие, товары, покупка, подтверждение. `expo-iap` про RuStore не знает |
| `supabase/functions/_shared/iap.ts` | `verifyRuStorePurchase` — запрос к `public-api-m.rustore.ru` по `purchaseId`, авторизация заголовком `Public-Token` (JWE), затем подтверждение покупки; у песочницы отдельный путь ([API RuStore](https://www.rustore.ru/help/en/work-with-rustore-api)) |
| `action: 'claim'` в функции `shop` | третья ветка проверки |
| `supabase/schema.sql` | `'rustore'` в `check (store in ('play', 'apple'))` у `shop_store_purchases` |

Вся остальная механика переиспользуется как есть: уникальный ключ платежа,
выдача после проверки, закрытие транзакции после выдачи, «Восстановить
покупки». Это и было смыслом того, чтобы проверка чека жила в одном месте.

### Что здесь не проверено

Честно о границах этого раздела:

- **Точные идентификаторы и методы Pay SDK не выписаны.** Хост
  `www.rustore.ru` закрыт сетевой политикой этой сессии, и выдумывать имена
  методов в инструкции, по которой кто-то будет делать, хуже, чем их не
  написать. Я завёл окружение **«Animation (RuStore docs)»**, где этот хост
  и `gitflic.ru` разрешены: выберите его при старте следующей сессии, и я
  допишу точные шаги со страницы Pay SDK для React Native.
- **Комиссия.** Источники расходятся: 15% в одном обзоре со ссылкой на
  п. 6.1 соглашения, и 0.9–3.35% до 1 млн ₽ с продукта плюс 15% свыше (10%
  для категории «Медиа») в [пресс-релизе
  VK](https://vk.company/ru/press/releases/11500/), который заметно старше.
  Сверьте с действующей редакцией соглашения в консоли — от этой цифры
  зависит весь выбор между путями А и Б.
- **Разрешённость альтернативных платежей** взята из блога RuStore и
  обзоров, а не из текста соглашения: прямого пункта найти не удалось.
  Перед запуском пути А имеет смысл перечитать [соглашение
  разработчика](https://help.rustore.ru/rustore/legal_info/developers_agreement).

## Отчёты об ошибках (Sentry)

Отчёты о падениях выключены, пока не задан `EXPO_PUBLIC_SENTRY_DSN`. Без
него все вызовы внутри `src/monitoring/sentry.ts` — пустышки, так что
локальная сборка и форк работают как раньше.

Чтобы включить:

1. Заведите проект на [sentry.io](https://sentry.io) (тип — React Native)
   и скопируйте **DSN**. Это публичный ключ: он позволяет только
   отправлять события, поэтому его место рядом с anon-ключом Supabase, а
   не в секретах.
2. Добавьте его в `env` профилей `preview` и `production` в `eas.json`:

   ```json
   "env": {
     "EXPO_PUBLIC_SENTRY_DSN": "https://…@…ingest.sentry.io/…"
   }
   ```

3. Для локального запуска — той же строкой в `.env`.

Стек в отчётах будет минифицированный: читаемым его делает загрузка
source maps, для которой нужен config-плагин `@sentry/react-native/expo`
с вашими `organization` и `project`. Добавлять его до появления проекта
смысла нет — плагин без этих значений ломает сборку.

В отчёт уходят модель устройства, версия системы, версия и номер сборки
приложения и стек ошибки; из аккаунта — только его идентификатор, без
имени пользователя (так написано в политике конфиденциальности, и код
это соблюдает).

## Android

Ничего настраивать не нужно: профиль `preview` даёт APK, который
скачивается по ссылке и ставится на телефон (нужно разрешить установку
из неизвестных источников).

### «Приложение не установлено»

Android отказывается ставить APK поверх уже стоящего, если не сходится
подпись — а подпись у сборки одна, пока не трогали ключ на EAS. Поэтому
первое, что стоит сделать: **удалить установленное приложение и поставить
заново**. Данные аккаунта от этого не теряются — они на сервере, локально
лежит только кэш.

Если не помогло, по порядку:

1. **Скачать APK заново.** Оборванная загрузка даёт ровно эту ошибку, а
   по размеру файла её не видно.
2. **Проверить разрешение** «Установка неизвестных приложений» именно у
   того приложения, из которого открываете файл (браузер или проводник) —
   оно выдаётся отдельно каждому.
3. **Отключить проверку при установке.** На Xiaomi/HyperOS и Samsung это
   «Сканировать приложения перед установкой» (Play Защита) и фирменная
   проверка безопасности — иногда она просто не отвечает и установка
   срывается без внятного текста.
4. **Посмотреть настоящую причину** через `adb install <файл>.apk` с
   компьютера: он печатает код вроде `INSTALL_FAILED_UPDATE_INCOMPATIBLE`
   (не сходится подпись) или `INSTALL_FAILED_VERSION_DOWNGRADE` (версия
   старее установленной), вместо «Приложение не установлено».

Профиль `preview` повышает `versionCode` на каждой сборке
(`autoIncrement`), так что новая сборка всегда новее установленной и
downgrade-отказ исключён.

## iOS

APK на iPhone не существует — там `.ipa`, и просто скачать файл нельзя:
iOS запускает только подписанные сборки. Варианты, от бесплатного к
полноценному.

### Expo Go — бесплатно, без аккаунтов

Ставите Expo Go из App Store, на компьютере `npx expo start`, сканируете
QR. Все нативные модули проекта (`expo-haptics`, `expo-image-picker`,
`expo-image-manipulator`, `expo-sharing`, `react-native-view-shot`) входят
в Expo Go, так что работает почти всё — кроме пуш-уведомлений, которых
Expo Go не поддерживает с SDK 53.

Это запуск внутри чужого приложения: своей иконки на экране не будет и
нужен работающий dev-сервер.

### iOS Simulator — бесплатно, нужен Mac

Профиль `simulator` собирает `.app` без всякой подписи и аккаунта Apple.
Запускается только в симуляторе на маке:

```
xcrun simctl install booted /путь/к/AnimeQuiz.app
```

### Apple Developer Program — $99/год, настоящая установка

Единственный способ поставить приложение на iPhone как обычное.

1. Оформите членство в [Apple Developer Program](https://developer.apple.com/programs/).
2. Свяжите аккаунт с EAS — один раз локально, интерактивно:
   ```
   npx eas-cli credentials
   ```
   EAS сам создаст сертификат и provisioning profile и сохранит их у себя;
   после этого сборки в GitHub Actions пойдут без вопросов. **Без этого
   шага сборка iOS упадёт** с `Failed to set up credentials. You're in
   non-interactive mode` — `--non-interactive` в workflow не умеет
   спрашивать пароль от Apple ID. Android при этом соберётся: задачи
   независимы.
3. Дальше:
   - **Ad-hoc** (`preview`): зарегистрируйте UDID устройства
     (`npx eas-cli device:create`), соберите — `.ipa` ставится по ссылке.
     До 100 устройств.
   - **TestFlight** (`production`): соберите, затем
     `npx eas-cli submit --platform ios`. Тестеров до 10 000, ставится как
     обычное приложение, но нужно пройти ревью Apple.

`bundleIdentifier` — `com.animequiz.app`, тот же, что и `package` у
Android. `usesNonExemptEncryption: false` в `app.json` избавляет от
вопроса про экспортные ограничения при каждой загрузке в App Store —
приложение использует только HTTPS, а это исключение из правил.
